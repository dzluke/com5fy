# 2026-11-10 · M2.6 Descriptor type

## What changed

**m5** (`mmmmm/`)
- New [`src/m5/descriptor.py`](../../../../mmmmm/src/m5/descriptor.py): `m5.Descriptor` (a plain dataclass) with
  - `series: {name: TimeSeries}`: `TimeSeries(times_ms, values, unit="", range=None)`, one value per time point
    (not necessarily evenly spaced; NaN = missing, e.g. unvoiced f0), with `value_range`;
  - `matrices: {name: FrameMatrix}`: `FrameMatrix(times_ms, frames, columns, units)`, one rows × columns matrix per
    frame (the number of rows can change, as with partials: `index, frequency, amplitude`, as in SDIF's `1TRC`);
  - `length_ms` (length of the analysed signal) and `duration`; `add_series` / `add_matrix` (chainable);
  - `to_bpf(name, interpolation)` → `m5.BPF` (M2.5) with the same name, unit and range; missing points are skipped;
  - `to_sequence(onsets=, pitch=, partials=, min_partial_ms=0)`: one note per onset (lasts until the next onset,
    pitched at the median of the pitch track in Hz/MIDI/midicents, written as the nearest pitch + `detuning_cents`),
    and/or one note per partial (amplitude-weighted mean frequency). Each source is its own staff, named after the
    descriptor. The other tracks' mean values over each note go into custom fields with the same names;
  - files: `from_file` / `to_file`, JSON (everything) and CSV (the series; or one frame matrix per file);
  - `str(descriptor)`: a summary with one line per track.
  Exported as `m5.Descriptor`, `m5.TimeSeries`, `m5.FrameMatrix`.
- No descriptor names are hard-coded (plan §8 item 6 is still open). The design choices are written down in plan §2.2
  under "Descriptor details".
- Fixture [`tests/data/melody.desc.json`](../../../../mmmmm/tests/data/melody.desc.json), generated by
  [`tests/data/make_descriptor_fixture.py`](../../../../mmmmm/tests/data/make_descriptor_fixture.py);
  22 tests in [`tests/test_descriptor.py`](../../../../mmmmm/tests/test_descriptor.py).
- **SDIF is not supported yet.** `pysdif3` (1.0.1, the latest release) can write SDIF files, but it can't open a plain
  `1TRC` partials file, which is the most common kind (it crashes on open). Details are in plan §2.2. `from_file` on a
  `.sdif` file says it isn't supported yet.

**com5fy**
- New type `M5_DESCRIPTOR` ([`nodes/types.py`](../../nodes/types.py)).
- **Load Descriptor** (`m5_LoadDescriptor`, `m5/io`, [`nodes/io.py`](../../nodes/io.py)): picks a `.json`/`.csv` file
  from `input/`, and runs again when the file changes. This is the file importer that M7.1 will build on.
- **Descriptor to Sequence** (`m5_DescriptorToSequence`, `m5/convert`, [`nodes/convert.py`](../../nodes/convert.py)):
  the descriptor → Sequence step of the conversion hub (plan §2.3). Widgets `onsets`, `pitch`, `partials` (descriptor
  names, blank = not used) and `min_partial_ms`. Its output goes into the existing Sequence Viewer.
- **Descriptor to BPF** (`m5_DescriptorToBPF`, `m5/convert`): one time series as a BPF (the "pick a descriptor as a
  BPF" part of M4.6; M4.6 will add rescale/threshold).
- These three nodes are meant to stay: they are the load node, the hub conversion and the control-data conversion.
  The only temporary part is showing the descriptor with Preview as Text until the Descriptor viewer (M3.5).
- Test workflow [`workflows/M2.6_descriptor.json`](../../workflows/M2.6_descriptor.json) (UI format) and
  [`workflows/api/M2.6_descriptor.json`](../../workflows/api/M2.6_descriptor.json) (for the runner); input file
  [`workflows/inputs/m5_melody.desc.json`](../../workflows/inputs/m5_melody.desc.json) (a copy of the m5 fixture).
- Tests: [`tests/test_descriptor_nodes.py`](../../tests/test_descriptor_nodes.py); node ids added in `tests/test_nodes.py`.

**Commits:** mmmmm `5489641`; com5fy: the commit that adds this note (M2.6).

## How to test

1. Restart ComfyUI (Python changed). Copy `custom_nodes/com5fy/workflows/inputs/m5_melody.desc.json` into ComfyUI's
   `input/` folder (`workflows/run.py` does this for you), then press R.
2. Open `custom_nodes/com5fy/workflows/M2.6_descriptor.json` and press Run.
3. What you should see:
   - **Loaded descriptor** (Preview as Text): `3 series, 1 matrix, 0–3000 ms`, then one line per track: f0 (Hz,
     range 50–2000, 2 missing), loudness (dB, −60–0), onsets (4 points), partials (60 frames, 0–3 rows of
     index, frequency [Hz], amplitude).
   - **Sequence Viewer**, two staves:
     - "onsets": A3, C4, E4, G4, each lasting until the next onset; the G4 has a −29 cents label.
     - "partials": the 3 harmonics of each note (12 notes), e.g. A3, A4, E5 +2.
   - **f0 as a BPF**, shown read-only (green) in a BPF node, like the BPF views in M2.5: "input 'f0': 58 points",
     exp, 0–2850 ms, range 50–2000 Hz. "Edit a copy" turns it into a curve you can draw on.
4. Things to try:
   - Blank `partials` or `pitch`.
   - Set `min_partial_ms` above 650: the G4's partials disappear.
   - Set `name` to `loudness` in Descriptor to BPF.
   - Type a name the descriptor doesn't have: the error lists the names it does have.
   - Use your own CSV: a `time_ms` (or `time_s`) column, then columns like `f0 [Hz]`. If time values repeat (one row
     per partial), the file is read as a frame matrix.

## Known limitations

- No SDIF (see above). No Descriptor viewer yet (M3.5); Preview as Text only shows the summary.
- Descriptor to Sequence:
  - Notes don't get velocities or dynamics, because loudness and amplitude come in different units.
  - Partial notes keep only the mean frequency, not the glissando.
  - A pitch track needs onsets (there is no segmentation by pitch alone).
- If a name in Descriptor to Sequence isn't in the descriptor, the node fails instead of skipping it. So with a
  descriptor that has no partials, you have to blank `partials`.
- CSV doesn't store ranges or `length_ms`. Missing values are written as `nan`.
- Load Descriptor and Load BPF both list every `.json`/`.csv` file in `input/`, so each one also shows the other's files.
- No Origin (M2.7) and no `to_dict`/`from_dict` (M2.8) yet. The JSON writer is a method of its own for now.

## Feedback wanted

- Is the structure right: generic named series plus frame matrices, with units and a nominal range? Should a range
  also be stored per matrix column?
- Descriptor to Sequence:
  - Are the default names `onsets` / `f0` / `partials` good, and should a name that isn't found fail or be skipped?
  - Should each onset note's pitch be the median of the pitch track?
  - Should loudness be turned into dynamics or velocities (and with which mapping)?
- Partials as notes: would you rather have each partial shown with its glissando, or chord-like groups per frame?
- The f0 BPF is drawn in its nominal range (50–2000 Hz), so a 220–390 Hz melody looks almost flat. Should the BPF
  view zoom to the data instead, or should Descriptor to BPF take the range from the data?
- Is the JSON/CSV layout right for the tools you use (Partiels, AudioSculpt, Max/bach, spreadsheets)? Does SDIF
  support matter enough to write our own small `1TRC`/`1FQ0` reader?

## Follow-up (2026-11-13)

- **SDIF: no.** Not supported and not planned (plan §2.2).
- **BPF range: zoom to the data.** A curve on a BPF node's `input` is now drawn over its data's min..max (+ 5%), so
  the f0 curve shows the four notes and their vibrato. "Edit a copy" still copies the nominal range (50–2000 Hz).
- The BPF editor layout changed too; see [`2026-11-13_M2.5.md`](2026-11-13_M2.5.md).
